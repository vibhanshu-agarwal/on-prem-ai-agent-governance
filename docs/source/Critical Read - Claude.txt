
Here's a critical read — not just restating the report's own caveats, but stress-testing the design for gaps it understates or doesn't fully close.
Overall feasibility: real, but harder than it looks on paper
The design is built entirely on components that exist today (LiteLLM, OpenLIT, Kubernetes, standard sandboxing runtimes) plus one custom layer — so it's not vaporware, and that's a genuine strength. But three things push it from "straightforward" to "moderate-to-high effort":
The custom control plane and bulk-kill action are real engineering projects, not configuration. The report says this explicitly, but it's worth being blunt in an exec framing: this is months of platform engineering, not a licensing purchase.
The sub-60-second stop target is aggressive once you account for four independently-owned systems (gateway, orchestrator, identity provider, network layer) each with their own propagation delay. The report calls its own numbers "recommended starting points, not guarantees" — that's an honest hedge, but it means the headline number in the exec summary is unproven until drilled.
Organizational coordination risk is understated relative to technical risk. Five leadership decisions, five different owning teams (platform, identity, SRE, security, architecture). The plan's success depends as much on cross-team discipline as on any single technology choice.
Loopholes the report doesn't fully close
1. Time-of-check/time-of-use gap is bounded for cost, not for harm. Output-token and time ceilings cap what a blocked agent's last request can cost. They don't cap what it can do in that window — send an email, call an external API, write to a database, delete a file. Cost and harm are treated as the same problem; they aren't. This deserves its own acceptance test, not just a spend-based one.
2. Delegation limits look like policy, not enforcement. "Sub-agents inherit narrower permissions than their parent, never broader" is a stated rule — but the report never says how that's enforced. If it's not cryptographically bound (e.g., attenuated/macaroon-style tokens where a sub-agent literally cannot mint a broader-scoped credential), it's a convention a compromised orchestrator can simply ignore.
3. Who watches the watchdog? The host-level watchdog is independent of the agent — good design. But if an agent achieves a true host-level breakout (the microVM tier exists precisely because this is possible), the watchdog running on that same compromised host is now also within the attacker's reach. The report doesn't address watchdog integrity after a confirmed host compromise.
4. The OpenLIT Controller's privileged access is flagged as a risk with no matching control. The report says twice that the Controller "runs with privileged infrastructure access" and "must itself be protected" — but never specifies how. That's a named gap with no design behind it yet.
5. Kubernetes NetworkPolicy on established connections is a real, unresolved hole. The report itself notes this is "implementation-defined" — meaning on some CNI implementations, a connection opened before quarantine (e.g., a reverse shell or an exfiltration stream) may keep flowing even after the policy is applied, unless the platform explicitly flushes conntrack state. This isn't a footnote; it's a plausible bypass of the entire "bulk quarantine" story. It should be its own acceptance test — the current 8 tests don't cover it (the "no bypass" test checks provider credentials, not live connection survival).
6. The identity register is a single point of both failure and compromise. Everything — kill switch, discovery, budgets — hangs off one governed identity per agent. That's good for control, but it also means the identity store itself becomes the highest-value target in the whole system. Compromising it could let an attacker impersonate any agent or mass-deactivate every legitimate one (a denial-of-service on the business, not just a security event). The "kill-plane outage" test covers availability of the stop mechanism; it doesn't test what happens if the identity store's integrity is compromised.
7. Isolation tiers are a policy, not a guardrail. "MicroVM for any agent executing model-generated code" is the right rule — but nothing in the design stops someone from deploying such an agent into a cheaper, weaker container tier by mistake. Without admission-control enforcement (e.g., policy-as-code that rejects a deployment if its declared capability doesn't match its sandbox tier), this is aspirational rather than guaranteed.
8. "Discovery proposes, humans approve" doesn't account for approval fatigue. Rate-limiting proposals per feed is a good day-one safeguard, but every human-approval gate at scale degrades into rubber-stamping over time — this is well documented in security operations generally. There's no mention of approval SLAs, sampling audits, or automated pre-screening to catch this decay.
9. Single-vendor concentration risk. The entire enforcement chokepoint is LiteLLM. The report's own sources section documents an actively-exploited RCE chain and a separate privilege-escalation chain against it in 2026. "Patch and monitor" is necessary but thin as the only mitigation for a single point of enforcement — no defense-in-depth (WAF in front, secondary validation layer, or a fallback path if the gateway itself is untrusted) is proposed.
10. Prompt injection isn't addressed at all. Every containment mechanism here assumes the agent becomes identifiably anomalous — spend spikes, unexpected processes, sandbox escape. But an agent compromised via prompt injection (malicious content in a document, webpage, or tool response) can misbehave entirely within its normal, authorized scope — no budget spike, no sandbox breakout, no network anomaly. That agent is invisible to every detection mechanism in this report until the damage is already scoped-in. This is arguably the most likely real-world "rogue agent" scenario in 2026 and it's not mentioned once.
11. Cost blind spots undercut the headline claim. The report's own Section 5 admits tool calls, SaaS APIs, storage, and GPU time sit outside the gateway's financial view. That means the "we can stop the budget bleed" story in the exec summary is true only for model spend — a meaningfully incomplete claim for a CXO audience unless caveated up front.
Bottom line
The architecture is sound and feasible using existing tooling, and the report is unusually honest about its own limits compared to typical vendor material — that's a real strength. But three categories of risk remain underbuilt relative to how confidently "Yes" is stated in the executive summary:
Enforcement vs. policy — several controls (delegation limits, isolation tiering, network quarantine completeness) are described as rules rather than backed by a mechanism that makes violation impossible.
Detection blind spots — prompt injection and in-window harm (vs. cost) aren't covered by any current test.
Concentration risk — one identity store and one gateway project are both single points of catastrophic failure with no stated fallback.
None of these are reasons to abandon the plan. They're reasons to add acceptance tests for connection-persistence-after-quarantine and in-window harm (not just cost), and to get explicit answers on delegation-token enforcement and admission-control for sandbox tiers before treating the "Yes" answers as fully closed.
