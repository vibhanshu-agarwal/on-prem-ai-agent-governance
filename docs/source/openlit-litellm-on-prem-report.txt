1. Executive summary

The proposed product is viable as an on-premises AI control plane, but neither open-source project alone is the
complete product. LiteLLM should provide the model gateway and request-path data plane. OpenLIT should provide
OpenTelemetry-based observability, traces, token and cost analytics, evaluations, prompts, and GPU visibility. A custom
control plane should provide agent identity, lifecycle controls, a synchronous spend ledger, versioned policy approval,
content-risk enforcement, model/vendor governance, auditability, and the single-window dashboard.

    Recommended product positioning: an on-premises AI agent control plane for cost
    governance, security policy, lifecycle management, and multi-provider accountability.

The licensing situation is favorable for proprietary wrappers, subject to preserving notices and avoiding LiteLLM
Enterprise source/features without a commercial license. There are no license-based request caps. Operational limits
come from gateway policies, provider quotas, local infrastructure, and the capacity of the synchronous enforcement
ledger.

A four-week delivery is feasible only as a supervised, customer-controlled pilot with a completed Week 0 entry gate and
deliberate descoping. It is not realistic to deliver a fully mature, multi-tenant, highly available enterprise platform with
broad providers, cloud billing governance, complete compliance evidence, and extensive hardening in four weeks.

5. Governance model and dashboard

Every request should carry a trusted, gateway-validated identity context. Do not rely on a user-supplied agent identifier.
Use a per-agent service identity or virtual key, and propagate a run/session ID through every LLM call, retry, tool call,
and delegation. The gateway should reserve budget synchronously before forwarding the request; delayed OpenLIT
telemetry must never be the only source used for a hard cap.

Governance object     Minimum fields or controls
Agent
                      agent_id, owner, version, endpoint, status, data classification, approved models, guardrail profile, tool
                      permissions.

Budget                Daily/monthly dollar cap, per-run dollar cap, input/output token limits, iteration limit, concurrency,
                      RPM/TPM, reservation ceiling, committed/released amount, and ledger sequence.

Request identity      Agent identity, run_id, parent_run_id, user/team, environment, cost center, provider, model, prompt
                      version.

Cost event            Input tokens, output tokens, cache/reasoning tokens where available, estimated cost, billed cost, local
                      inference cost, latency, retries, result status.

Audit event           Who changed the policy, what changed, previous value, new value, approval, effective time, rollback
                      version.

Policy bundle         policy_id, version, draft/approved/effective/retired state, diff, author, approver, signature, effective time,
                      expiry, and rollback target.

Model/vendor profile  Provider, model and version, data classification, residency, retention, terms, evaluation status, deprecation
                      date, approved use cases, and risk owner.

Failure mode          Dependency, default action, fail-closed scope, break-glass role, reason, TTL, approver, and post-incident
                      review.

The dashboard should provide an agent control center, cost and token analytics, model economics, guardrail/risk views,
model/vendor approval views, policy diffs and approvals, ledger health, break-glass activity, and audit/operations views.
It should distinguish total spend from unit token price and from cost per successful task.

For strict dollar caps, add atomic budget reservation before the request is forwarded. LiteLLM spend logging is
documented as asynchronous after the response, which can otherwise permit overshoot under concurrency, retries,
streaming, and telemetry lag. Reserve a conservative maximum, commit actual usage, release unused capacity, and
reconcile the ledger to OpenLIT evidence by run ID.

Content risk controls belong inline in the data plane: pre-call PII detection/redaction, prompt-injection and sensitive-topic
checks, tool/MCP authorization, and post-call output filtering/DLP. A guardrail outage should fail closed for the affected
data classification unless an approved break-glass policy applies.

8. Market potential and differentiation

The opportunity is real, but the gateway layer alone is increasingly commoditized. LiteLLM already covers much of the
basic provider abstraction and gateway functionality. The stronger commercial product is the regulated-enterprise
control plane around agents, budgets, security, audit, and cost reconciliation.

The best initial customers are banking, healthcare, government, defense, manufacturing, and large enterprises
operating private data centers or sensitive workflows. The likely buyer set includes platform engineering, AI Centers of
Excellence, security, FinOps, and CFO organizations.

Potential differentiation: air-gapped/on-prem deployment, trusted agent identity, per-run hard budget enforcement,
versioned policy approvals, inline content-risk controls, model/vendor risk decisions, tool/MCP governance, auditability,
and later cloud invoice reconciliation. A reskinned LiteLLM dashboard would be much harder to defend.

9. Four-week supervised pilot feasibility

Verdict: four weeks is defensible only as a supervised pilot after a completed Week 0 entry
gate and deliberate descoping. Without those conditions, the scope is a 6-8 week effort, not
a four-week delivery.

This is a customer-controlled pilot, not a production-grade platform. The operating posture is fail-closed for new requests
when identity, policy, ledger, or required guardrail dependencies are unavailable; there is no HA/DR in the pilot.
Proposed pilot SLA: 99% availability during agreed business hours, business-hours support, and no 24x7 production
commitment. The customer accepts request rejection during maintenance or dependency outages.

A credible team is approximately three to five experienced engineers: one platform engineer dedicated to the ledger and
gateway path, one engineer for agent adapters and control-plane configuration, one frontend/observability engineer,
DevOps/SRE support, and part-time security support. The customer owns agent-side code changes and provides an
operator; the gateway team owns the integration contract and enforcement path.

Critical-path semantics:

 - Ledger first: reserve an upper-bound cost before forwarding, commit actual usage, release unused capacity, and make
    reserve/commit/release idempotent with lease expiry. OpenLIT evidence reconciles the ledger but never replaces it.

 - Streaming: every request must provide max_tokens or receive an agent-specific default ceiling; unbounded streams are
    rejected. Reserve input estimate plus the output ceiling, commit at stream end, release unused capacity, and terminate
    the stream with an explicit budget event if the reservation is exhausted.

 - Latency SLO: measure provider-free overhead separately. Proposed pilot pass target is p95 <= 150 ms and p99 <= 300
    ms for ledger, policy, and guardrail processing on prompts up to 8K input tokens, plus no more than 10% overhead for
    calls whose provider latency exceeds 1.5 seconds. Tune the target at the Week 0 baseline.

 - Guardrails: no hosted moderation dependency is assumed for air-gapped operation. The selected self-hostable engine
    and false-positive/override behavior must be demonstrated before Week 2 closes.

 - Agent integration: the gateway team publishes the run_id/parent_run_id contract in Week 0; each agent owner
    implements and tests propagation through LLM calls, retries, tools, and delegation in Weeks 1-3.

Suggested sequence:

 - Week 0: complete the entry gate; freeze the workload, SLO, deployment, identities, approved providers/models,
    guardrail engine, OSS versions, SBOM process, owners, and Git policy repository.

 - Week 1: build and load-test the synchronous ledger first; implement reserve/commit/release, idempotency, lease expiry,
    streaming ceilings, minimal LiteLLM wrapper, one provider/local endpoint, and one agent adapter.

 - Week 2: add trusted identity, enable/disable, signed Git policy bundles, model allowlists, minimal self-hostable
    guardrails, and the second agent adapter. End with a midpoint checkpoint: ledger and agent correlation must work
    under representative load or the delivery moves to 6-8 weeks.

 - Week 3: integrate the remaining pilot agent, OpenLIT/Grafana cost evidence, thin status page, reconciliation, second
    provider if allowed, latency measurement, and targeted security tests. No custom approval UI or broad dashboard build.

 - Week 4: run focused concurrency, streaming, outage, rollback, backup/restore, SBOM/notice, and customer acceptance
    tests; package the deployment; hand over the runbook; and start supervised pilot traffic.

Minimum pilot acceptance criteria:

 - Every pilot request is attributed to agent, run, user/team, provider, model, tokens, and cost, including retries, tools, and
    delegation.

 - Ledger hard caps show zero overshoot in concurrency, retries, fallbacks, streaming, and delayed telemetry tests;
    reservation release and idempotency are verified.

 - Requests without max_tokens are bounded by an agent default; exhausted streaming reservations terminate with an
    auditable budget event.

 - Gateway/policy/ledger/guardrail outages fail closed for new requests, while evidence-plane outages do not bypass
    enforcement. Break-glass is time-limited and audited.

 - Policy changes use Git PR approval, immutable diffs, effective versions, and rollback; no bespoke approval UI is
    required for the pilot.

 - The selected self-hostable guardrail engine meets the Week 0 latency target and has documented false-positive
    handling and redaction behavior.

 - The pilot meets the proposed p95 overhead budget and has a named operator, business-hours support path, outage
    runbook, and backup/restore test.

 - The delivered image includes pinned versions, SBOM, third-party notices, deployment instructions, and rollback
    instructions.

Pilot success is measured separately from feature acceptance: default target is five consecutive business days of
supervised traffic and at least 1,000 requests, or the customer's agreed equivalent, with zero hard-cap overshoots, no
unresolved Sev-1 security incident, and the p95 overhead target met. If the target is not reached, the result is a pilot
extension or 6-8 week plan, not a claim of production readiness.

10. Final recommendation

Proceed with a hybrid architecture and call the first release a four-week supervised pilot, not a production platform. Use
LiteLLM OSS for the gateway foundation and OpenLIT OSS/Grafana for observability, keep the custom control plane
thin, and use Git-reviewed policy-as-code instead of building approval and dashboard breadth during the pilot. The initial
review is correct that the ledger and agent integration are the critical path.
Before the four-week clock starts, obtain these decisions from the customer:

 - Exact deployment target: Kubernetes, Docker, air-gapped, or restricted-egress environment.
 - Expected peak concurrent requests, average prompt/output sizes, and monthly request volume.
 - Approved model providers and whether sensitive prompts may leave the premises.
 - Data classifications, model/vendor approval criteria, version/deprecation policy, and permitted break-glass behavior.
 - Identity integration: OIDC/LDAP/reverse proxy and required RBAC roles.
 - Pilot acceptance criteria, especially hard dollar caps, streaming behavior, p95 overhead, guardrail behavior, outage

    semantics, audit, backup/restore, and rollback.

    Go/no-go rule: do not start Week 1 until the Week 0 entry gate is signed off. If the ledger,
    agent correlation, or representative latency target is not demonstrated at the end of Week 2,
    replan as a 6-8 week delivery.
