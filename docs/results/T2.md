# T2 results: hard budget caps

Date: 2026-09-29. Gateway: LiteLLM `v1.100.3` (T1 pin), native budget reservation on,
`fail_closed_budget_enforcement: true`.
Result: **36/36 tests pass** (`tests/budget`, clean run: the isolated stack was brought up from scratch and torn down, 9 min 52 s). After that run I tightened two tests (retries now always exercised; the Redis-restart burst waits for recovery) and re-ran both: pass. **Zero overshoot in every guarded test.** Eight `native_baseline` tests reproduce the native LiteLLM overshoots that the guard closes. The fail-closed and request-body-fallback tests also measure both gateways.

Run: `uv pip install -r tests/budget/requirements.txt`, then
`.venv/Scripts/python -m pytest tests/budget -rA` (about 10 min; brings up and tears down the
isolated stack itself, `T2_KEEP_STACK=1` keeps it). Measured values land in
`.local/t2/results.json`.

## How the tests are set up

- **Isolated stack.** Everything that stops, kills or restarts a container runs on a separate
  compose project, `govpilot-t2` (`tests/budget/stack/`): an override on `deploy/docker-compose.yml`
  with its own container names, networks, volumes and ports. The shared `govpilot` stack is never
  stopped.
- **Two gateways, one backend.** `t2-gateway` (127.0.0.1:4100) runs the production config with the
  budget guard. `t2-gateway-native` (127.0.0.1:4101) runs the same config without the callback, so
  LiteLLM's native behaviour is measured on the same Postgres, Redis and mocks. Both configs are
  generated from `deploy/litellm/config.yaml` (`t2stack.py`), so they cannot drift from production.
  The only test-only additions are: a dead-port deployment with a router fallback to `mock-remote`;
  a group with one dead and one live deployment (retries, with router cooldowns disabled so retries always happen); a runaway provider; and
  `proxy_batch_write_at: 15` (production uses 5) to widen the DB lag window.
- **Runaway provider** (`tests/budget/stack/runaway_provider.py`, test fixture only). It ignores
  `max_tokens` and always streams 600 tokens, which is what a non-conforming provider looks like.
- **Tests named `native_baseline`** assert that a native gap still reproduces. If a LiteLLM upgrade
  makes one fail, the matching guard feature may be removable.
- **Where spend is measured.** From the `x-litellm-response-cost` header, the Redis spend counter
  (`spend:key:<hash>`, `spend:team:<id>`), the Postgres key spend, and `LiteLLM_SpendLogs`.
- **Prices** (from the config). mock-local is $1/$2 per M input/output tokens; mock-remote is
  $5/$15. A standard request (7 prompt tokens, `max_tokens=100`) costs $0.000207 on mock-local.
  Native reserves $0.000211 for it, because the tiktoken input estimate is 11 tokens.

## Gaps found in native LiteLLM v1.100.3 (all reproduced by tests)

1. **Partial reservation admits the last request (sequential, no concurrency needed).** When a
   counter is over budget but some budget is left, `budget_reservation.py` resizes the reservation
   down to what is left and still admits the request. The request then costs its full price.
   - Per-key overshoot is bounded by the cost of one request. That was +3.5% with $0.002 on
     mock-local, and **+50.4%** with a $0.02 cap on mock-remote at 1000 tokens.
   - Team caps behave the same way (+3.5% across three keys).
2. **No per-key `max_tokens` ceiling (T1 finding, confirmed).** `max_tokens=100000` is forwarded
   while the reservation is clamped at `max_output_tokens` (1024). One request spent $0.008199 on a
   $0.002 key, **4.1x the cap**.
3. **Fallbacks are priced on the requested model only.** A router fallback (or a client-supplied
   `fallbacks`) from mock-local to mock-remote reserved $0.000411 and spent $0.003035. That is
   **+51.7% over the key's $0.002 cap** in one request. The key's model allowlist *is* enforced
   on request-body fallbacks (403).
4. **Runaway provider.** Native streams all 600 tokens against a 50-token reservation: **10.9x the
   reservation**.
5. **Delayed telemetry plus counter TTL (single fault).** Redis spend counters expire 60 s after
   their last write and are then reseeded from Postgres `key.spend`. A gateway restart inside the
   `proxy_batch_write_at` window loses the queued `key.spend` increment. That happened even on a
   graceful `docker restart`; `key.spend` stayed at 0. After 60 s idle, the key could spend its
   budget again: **+107%** (total $0.00414 on a $0.002 cap).
6. **Postgres down.** Native keeps admitting budgeted requests from its in-memory auth cache for
   **~90 s** (12 requests admitted in the test). The Redis counter still capped spend, so this is not an
   overshoot, but spend logs cannot be written while the DB is down.
7. **Redis down (native is fine).** Budgeted requests get a 503 (fail closed). The first rejection
   takes ~19 s (socket timeouts); later ones are immediate.
   - After Redis returns, the client circuit breaker keeps failing closed for up to ~60 s, then
     enforcement resumes against the persisted (AOF) counters.
   - Keys and teams with no budget keep working, because there is nothing to enforce.

Retries were not a gap: a retried request is billed once, and dead-deployment attempts cost nothing.

## What I built, and why

Everything is in **`deploy/litellm/callbacks/budget_guard.py`**, one LiteLLM `CustomLogger`. It
is wired through `litellm_settings.callbacks` and a read-only `./litellm/callbacks:/app/callbacks`
mount; the compose and config edits are 1 and ~10 lines. No custom ledger was needed; see the
note at the end of this section.

The key constraint is ordering. Native reservation runs during **auth**, before any pre-call hook.
So the guard does not re-implement reservation. It **shapes the request so that worst-case cost is
no more than what was already reserved**.

- **Pre-call: `max_tokens` ceiling and default** (gap 2).
  - The ceiling is the minimum of the agent policy and every reachable model's `max_output_tokens`.
  - A request above the ceiling is rejected (400 `max_tokens_exceeds_ceiling`) or clamped,
    depending on policy.
  - When `max_tokens` is absent, the agent default applies, else the model's
    `litellm_params.max_tokens`.
  - `max_tokens`, `max_completion_tokens` and `max_output_tokens` are all handled.
- **Pre-call: fit the reservation** (gaps 1 and 3).
  - The guard reads `user_api_key_dict.budget_reservation.reserved_cost`.
  - It computes the worst case over the requested model plus every router or request-body
    fallback, using LiteLLM's own public estimator functions, so the numbers match what auth
    reserved.
  - If the worst case exceeds the reservation, the request is rejected (429 `budget_exceeded`).
    With `on_insufficient_reservation: clamp`, `max_tokens` is instead cut to what the reservation
    affords.
  - The failure hook releases the reservation, and the counter returns to 0.
  - A budgeted, priced request with no reservation at all is rejected (fail closed).
- **Streaming guard** (gap 4).
  - The guard counts output chunks. Once a provider exceeds the enforced ceiling, it closes the
    upstream and emits a final chunk with `finish_reason: "length"`.
  - It bills the partial output through LiteLLM's disconnect-billing path, which reconciles the
    reservation and writes the spend log.
  - It then emits a `budget.stream_terminated` event.
- **Non-streaming overrun detection.** A `budget.provider_exceeded_max_tokens` event. The cost has
  already been incurred, so it is billed truthfully.
- **Postgres fail-closed gate** (gap 6). A background `SELECT 1` runs every 2 s. Budgeted requests
  are rejected (503 `budget_enforcement_unavailable`) once the DB has been unreachable for 5 s.
  Measured: the first rejection came 4.3 s after the DB stopped.
- **Spend-counter TTL** (gap 5).
  - `litellm_settings.default_redis_ttl: 2678400` (31 days, which is at least the 30-day
    `budget_duration`).
  - v1.100.3 builds the coordination Redis *before* it reads `litellm_settings`, so the guard
    applies that value to the spend-counter Redis client.
  - Counters then survive the budget period in AOF-persisted Redis. The lagging, lossy `key.spend`
    is no longer the reseed source after idle. The budget reset job rewrites counters itself.
- **Loose coupling.**
  - Two small ports:
    - `PolicySource`: adapter `KeyMetadataPolicySource`, which reads key metadata `token_policy`,
      then team metadata, then env.
    - `BudgetEventSink`: adapter `LogEventSink`, one `GOVPILOT_BUDGET_EVENT {json}` line on
      gateway stdout. It is selected by `GOVPILOT_BUDGET_EVENT_SINK`; T3's AuditSink can replace it.
  - All limits come from key/team metadata or env; nothing is hard-coded per agent.
  - Per-agent config example (key or team metadata):
    `{"token_policy": {"max_tokens_ceiling": 512, "default_max_tokens": 256, "on_exceed": "reject", "on_insufficient_reservation": "reject"}}`

**No custom ledger (`services/ledger/`).** Every overshoot the tests found is closed by native
reservation plus request shaping plus the counter TTL. The remaining DB drift (below) is a
reporting and durability problem, not a cap overshoot, so a ledger is not justified yet.

## Residual risks and open issues

- **DB spend drift after a gateway crash or restart.** Up to one `proxy_batch_write_at` window of
  spend can be lost from Postgres. That covers `key.spend` always, and spend-log rows sometimes:
  lost on one SIGKILL run, present on another.
  - The Redis counter keeps the true value and keeps enforcing the cap.
  - But `/key/info` and any dashboard reading Postgres under-report. If Redis also loses its data
    (a double fault), the reseed would use the stale DB value.
  - Proposed fix, if it matters: a small ledger reconciler that restores key/team spend from
    `LiteLLM_SpendLogs` at gateway start, run while quiescent. It is racy with live multi-pod
    traffic, so it needs a pod lock. Alternatively, lower `proxy_batch_write_at`.
- **Runaway streaming bound.** The guard can only detect an overrun once the extra chunk arrives,
  and bills it. The measured overrun is at most **one token** beyond the reservation ($2e-6 here).
  Zero overshoot holds for providers that honour `max_tokens`.
  - Non-streaming overruns cannot be cut at the gateway; they are detected and billed. Provider
    conformance to `max_tokens` is a precondition; add a conformance test per real provider.
- **Input-token estimate.** Reservation uses tiktoken. The mock counts fewer tokens, so it is
  conservative here. A real provider whose tokenizer counts more than tiktoken could exceed the
  reservation by the difference. `GOVPILOT_BUDGET_GUARD_INPUT_SAFETY` (default 1.0) adds a margin.
- **Fallbacks to pricier models** are rejected by default when the reservation, priced on the
  primary, cannot cover them. Agents that need that fallback should use
  `on_insufficient_reservation: clamp`, or call the pricier model directly.
- **Private LiteLLM internals.** The guard uses two:
  - `_bill_partial_streamed_spend_on_disconnect`, for stream-cut billing. If it is missing, the
    guard falls back to keeping the full reservation as spend (conservative).
  - `spend_counter_cache.redis_cache.default_ttl`, for the TTL pin.

  The suite's `native_baseline` and TTL assertions will flag a LiteLLM upgrade that changes either.
- **Single guarded gateway.** Multi-instance gateways share the Redis counters, so they should
  behave the same, but only one guarded instance was tested.
- **Redis outage recovery.** Fail-closed continues ~60 s after Redis is back (circuit breaker).
  That is safe but costs availability; tune with `REDIS_CIRCUIT_BREAKER_RECOVERY_TIMEOUT`.
- **Shared stack.** The shared gateway container was recreated once (`up -d --no-deps gateway`) to
  mount the callback. `tests/foundation`: 30/31 pass. The one failure,
  `test_providers_network_members_and_internal_flags`, is caused by `gov-gateway-otel` (project
  `govpilot-obs`, T6) joining `govpilot_providers`, not by T2.
- The T1 agent keys (`scripts/provision.py`) carry no `token_policy` yet, so they get the
  model-level defaults (ceiling 1024, default 256). T4 should set per-agent policies in key metadata.
