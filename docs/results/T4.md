## The run model

```
task run (one loop iteration)                        run-a1..  parent=-          root=run-a1..
  |-- tool run  rewrite_query                        run-b2..  parent=run-a1..  root=run-a1..
  |-- tool run  classify_exception  (LLM inside)     run-c3..  parent=run-a1..
  |-- delegation run (child agent, own key)          run-d4..  parent=run-a1..  agent=finance-recon-agent.variance-analyst-<epoch>
  |     each LLM call of a run = step 1, 2, 3 ...    each retry of a step = attempt 1, 2, ...
```

- A request is uniquely `(run_id, step, attempt)`. **Retries keep the run id, parent, root and step** and bump `attempt`; a run that calls the model several times numbers its calls with `step` (found the hard way: the first live attribution test paired rows by `(run, attempt)` and the delegated child made two calls in one run).
- Fields travel as `x-govpilot-run-id | parent-run-id | root-run-id | run-kind | step | attempt | tool | user` headers **and** as LiteLLM's own `x-litellm-spend-logs-metadata` header, plus a W3C `traceparent` derived from the run tree, plus the OpenAI `user` field (end user). The second carrier means attribution still works if the gateway callback is missing or refuses to run (the rows then just lack the trusted agent/team stamp).
- Run ids: `run-<16 hex>`, grammar `^[A-Za-z0-9][A-Za-z0-9_.:-]{5,79}$`, identical in the library and the callback (a test compares them).

## The gateway callback (`run_attribution.py`)

- **Pre-call:** validates the run fields, then writes `metadata.spend_logs_metadata` with the **trusted** `agent_id` / `team` / `key_alias` / `root_agent_id` / `parent_agent_id` taken from the virtual key (a test proves an agent cannot claim another agent's identity through the metadata header), plus the run fields. Sets the spend-log `session_id` to the run id and an `agent:<id>` tag (low cardinality; never one tag per run).
- **Modes**, from key metadata `attribution.mode`, else team metadata, else env `GOVPILOT_ATTRIBUTION_MODE` (default `audit`):
  - `enforce`: no or malformed run id is refused with 400 `run_id_required`; a good run id with broken tree fields (a tool run with no parent, bad step/attempt) gets 400 `run_fields_invalid`.
  - `audit`: lets it through, stamps `attribution: missing_run_id`, emits an event.
  - `off`.
  The three sample agents' keys are `enforce` (set in `deploy/agents.json`); every other key stays `audit`, so T1/T3/T6 tooling is not broken. One consequence: anything that uses the pilot agent keys directly now needs `x-govpilot-run-id`; `tests/foundation` gained one header line for that.
- **Response headers:** `x-govpilot-run-id`, `-agent`, `-step`, `-attempt`, `-attribution` echo what was recorded.
- **Per-attempt event:** one `GOVPILOT_ATTRIBUTION {json}` line per success or failure (agent, run, parent, step, attempt, tool, user, model, provider, tokens, cost, error). The sink is a port (`AttributionEventSink`, one `log` adapter), like T2's `BudgetEventSink`.
- Loaded after `budget_guard`; `budget_guard.py` was not touched. A pitfall recorded for the next callback author: LiteLLM imports these files without registering the module in `sys.modules`, so `@dataclass` (with `from __future__ import annotations`) crashes the gateway at start-up; the callback uses a plain class.

## Querying attribution

```
$ python scripts/attribution_report.py --since 20m --agent finance-recon-agent --tree
run-c9e4d64d4cb84978  task  agent=finance-recon-agent  reqs=1  own=$0.000845  subtree=$0.001465  mock-remote/mock-remote
  run-66a040c90552422c  tool:classify_exception  agent=finance-recon-agent  reqs=1  own=$0.000074  ...  mock-local/mock-local
  run-a9f1bf4033c34b31  delegation  agent=finance-recon-agent.variance-analyst-1790683118  reqs=2  own=$0.000176  ...
```

Views: per agent/team/user/provider/model/run/root/kind (`--by`), every request (`--rows`), run trees with roll-up (`--tree`, `--run <id>`), `--json`, `--check` (exit 1 on any unattributed spending request), `--from-json` for rows saved from another gateway (the `normalise()` function is the contract). Every report ends with a completeness line: attributed / rejected before any spend / unattributed.

What counts as a hole: a request that has no run id **and** cost something or was served. A request refused before spending anything is `rejected`, not a hole.

## Loop rate and the "go rogue" demo

`deploy/agents/config/rates.json` (directory-mounted, re-read on change, no restart) holds `interval_s`, `jitter`, `concurrency`, `max_tokens`, `on_budget_exceeded`, `paused`, `profile`; env vars sit below it, the per-agent entry above it.

```
python scripts/agents_ctl.py rogue finance-recon-agent   # 0.05 s interval, 4 in parallel, keeps hammering when refused
python scripts/agents_ctl.py calm  finance-recon-agent   # restores exactly the previous rate
```

Live proof (`test_rogue_rate_profile_burns_the_budget_and_the_gateway_refuses_the_rest`): a throwaway coding-agent key with a $0.004 cap, calm at 1 iteration/s, flipped to rogue by editing the mounted file (the running container logged `loop.settings profile=rogue` without a restart). Three consecutive runs on a quiet gateway (`.local/t4-results/rogue_demo.json`): 37 to 57 requests each, 17 to 37 refused by the gateway, **$0.003901 spent of $0.004 every time**, the key spend in Postgres equal to the sum of the spend logs, 13 to 34 further attempts made by the hammering agent after its first refusal. Every request that spent money is attributed to its run; every refusal is attributed to the agent, but only some refusals (5 to 11 of the 17 to 37) carry the run, see finding 1.

## Findings, deviations, limits

1. **Refusals during LiteLLM auth carry no run id.** A blocked/unknown key, an off-allowlist model, a stopped agent and, most often, a key whose budget is already used up are refused before any hook runs. The failure row names the key (agent) and the error, has cost 0, and cannot carry the run (in the rogue demo roughly a quarter to a third of the budget refusals still carried it, the rest were refused at auth). The report classifies these as `rejected` (not holes) and tests pin the behaviour. Refusals raised inside hooks (token ceiling, budget guard when the reservation does not cover the request, guardrails, run-id enforcement) keep the run fields, because the adapter also sends LiteLLM's native metadata header. Consequence for an auditor: spend is always attributed to a run; a denied attempt is always attributed to an agent, and to a run only when the denial happened inside the hooks.
2. **No update endpoint in the control-plane API.** Binding the SSO subject, syncing capabilities and setting the `workload_image` label on the seeded agents is done by `scripts/agents_provision.py`, which runs the control plane's own domain service inside its container (`docker exec`) and writes an audit record per change. A small `PATCH /v1/agents/{id}` would be cleaner; not added because `services/control-plane` is T3's.
3. **Capability names (fixed in review).** T3's seed and admission rule used `executes_code` (and `calls_tools -> gvisor`); T7 uses `executes_model_code` (and `calls_tools -> container`). The review made T3's `CAPABILITY_MIN_TIER` mirror `policy/global.yaml` (one vocabulary: `executes_model_code`, `external_send`, `calls_tools`), renamed the seed, and `agents_provision.py` now runs the register's own `check_admission` before writing capabilities (it used to bypass it). The running control plane picks this up on its next rebuild.
4. **Agents cannot reach the control plane, by design**, so delegation goes through `delegation-broker` (`gov-delegation-broker`, on `govpilot_agents_sso` and `govpilot_cpinternal`), which forwards exactly `POST /v1/delegations`. The base `agents` network still has one member. The broker carries no agent label (`govpilot.role=platform`); T6's discovery feed may propose it, and would need an ignore rule.
5. **`workload_image` label (T6 spoof check).** All three agents are registered with `labels.workload_image = govpilot/agents:1` (from `deploy/agents.json`), the tag rather than a digest so a rebuild does not look like a spoof; a test keeps `agents.json` and the compose file in agreement. Tightening to a digest is a config change.
6. **Delegable budget is consumed by children.** Each minted child reserves its budget from the parent's remaining delegable amount for as long as it is active, and the register has no way to retire a child short of a stop. The Finance agent mints one child per day (0.2 of 2.0, so about 9 days of delegable budget; at one hour it would have run out in 9 hours, which is why the lifetime is 24 h). Repeated live test runs mint small ones (0.005) and delete their gateway keys, but the register entries remain, so a long run of tests will also eat into it (about 300 test runs). A child that exhausts its own $0.2 is refused by the gateway like any agent, and the delegation fails for that iteration.
7. **The shared gateway was redeployed several times by other work streams while the live suite ran** (T5 iterations); a redeploy mid-test breaks agent runs. `tests/agents/livelib.py` waits for the gateway to be up for 75 s, refuses to run against a gateway older than the callback file, and re-runs a test if the gateway was recreated during it (a failure with the gateway untouched is raised as is).
8. **One unexplained overshoot, not reproduced (review assessment below).** In the first rogue run, spend-log rows summed to $0.004014 against the $0.004 cap ($0.000014, exactly one 4-in/5-out mock-local request, 0.35 percent), at a time when the shared gateway was being recreated by another work stream. Five later runs stayed under the cap ($0.003913, then $0.003901 four times). T2's residual-risk note (spend lost or re-granted around gateway restarts) is the likely place to look; the test asserts the cap strictly and prints the last rows if it ever fires.
   Review assessment: probably a real, bounded gap in the restart path, not in the guard's shaping logic. The overshoot equals one request, and the rogue agent had 4 requests in flight when the gateway was recreated. Two mechanisms fit. (a) A request served by the old gateway had its spend-log row written, but its Redis counter increment or reservation reconcile was lost at SIGTERM, so the new gateway admitted one request too many. (b) The client disconnect ran the failure hook, which released the reservation of a request the provider had already served. Either way the bound is in-flight concurrency x the worst-case cost of one request. What T8 should test, on the isolated stack: a budgeted key within about 3 requests of its cap, driven 4-way concurrent; recreate the gateway (`up -d --force-recreate`, plus `kill -9`) at random offsets while requests are in flight, 20 or more times. After each: (1) compare the Redis spend counter, `key.spend` and the sum of spend-log rows right after restart, then again after draining the key to refusal; (2) assert the spend-log sum stays at or under the cap; (3) look for spend-log rows with no counter increment, and for released reservations whose request still produced a success row; (4) look for duplicate `(run_id, step, attempt)` rows across the restart. If it reproduces, the fix belongs in `budget_guard.py`: reconcile the counter from spend logs at startup, or keep reservations on client disconnect until the provider call settles.
9. Reading the spend logs needs the master key; a real deployment would use a read-only reporting credential or query a warehouse copy.
10. The Docker healthcheck tracks the loop heartbeat (900 s allowed, because a budget-refused polite agent backs off up to 300 s), so a stopped agent shows unhealthy, not missing.

11. **Review hardening (2026-09-29).** (a) `enforce` now covers every call type except a short non-spending list. The old allowlist covered chat/embeddings/responses only, so `aimage_generation`, `aspeech`, `arerank`, pass-through and similar routes skipped the run-id check. (b) An attribution policy that is present but unreadable (`"Enforce"`, a wrong type), or an invalid `GOVPILOT_ATTRIBUTION_MODE`, now resolves to `enforce` instead of `audit`. (c) The delegation broker strips the child's raw `gateway_key` from the mint response. That key has no expiry caveat and skips the auth proxy's lineage and model checks, so an agent could otherwise keep using it after its delegation token expired. Open limit (not fixed): the report takes `agent_id` from `spend_logs_metadata`. That value is trusted only when the callback ran. If the callback is missing or set to `off`, the stored metadata is the caller's own `x-litellm-spend-logs-metadata` header, so the agent name there is caller-asserted. `user_api_key_alias` stays trustworthy. A key alias cannot simply override it, because several legitimate keys have an alias that differs from their `agent_id` (rotated keys, test and bench keys). The fix is to resolve `agent_id` from the key's own metadata through `/key/info`, keyed by the `user_api_key` hash in the row. Until then, `--check` is only an identity guarantee on a gateway where the callback is loaded, which `livelib` verifies. Re-run after the review: `tests/agents` 120/120 pass. That includes the 13 live tests, run against a gateway that had loaded the edited callback; the new callback was also exercised inside the gateway container with the real LiteLLM.

## Simplifications vs an enterprise deployment

| Here | Enterprise | Swap |
|---|---|---|
| Run ids are minted by the agent library | trace ids from the service mesh / OpenTelemetry SDK | `RunContext` (the header names are the contract; `traceparent` is already sent) |
| Spend logs in LiteLLM's Postgres, report via admin API | warehouse table fed by the `GOVPILOT_ATTRIBUTION` events | `AttributionEventSink` adapter; `normalise()` |
| Delegation broker (stdlib forwarder) | service-mesh egress rule or a control-plane endpoint on the agent network with its own auth | `BROKER_URL` |
| Mock model output, fixture code, compile-only sandbox | real model, microVM sandbox executing model code | tier label + admission (T7) |
| Loop rates in a JSON file | scheduler / queue consumer concurrency limits | `AgentRuntime` |
